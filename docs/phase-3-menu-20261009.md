# Phase 3 — catalogue / menu, premier lot du 9 octobre 2026

## Autorisation et périmètre

Après la validation fonctionnelle de Phase 2, l'utilisateur autorise explicitement
la Phase 3. Réserves de clôture : `cloture-phase-2-20261009.md`. Le périmètre
reste le navigateur ; aucune commande, paiement, mouvement de stock ou application
Android n'est ajouté. Références : cahier des charges §4.4, §7, §8, RG-09/RG-10.

## Développé

- Catégories nommées, actives/désactivées, sans suppression physique.
- Produits : code unique normalisé, nom, catégorie, description, prix USD,
  statut, disponibilité et photo. Recherche et filtres serveur ; listes et
  historique des prix paginés. Interface responsive, chargement, erreurs et
  absence de résultats traités.
- Prix `DECIMAL(12,2)` en base, chaînes décimales dans l'API. Valeurs négatives,
  exposants et fractions de centime refusés. Zéro autorisé ; aucune conversion
  de devise ni calcul de commande dans ce lot.
- Prix initial et changements conservés dans `menu_price_history`, avec ancien
  prix, nouveau prix, auteur et date. Produit, historique et audit sont écrits
  dans la même transaction. Une représentation équivalente (`0.20`/`0.2`) ne
  crée pas un faux changement de prix.
- Produit vendable seulement si actif, disponible et rattaché à une catégorie
  active. Désactiver une catégorie conserve les produits et les rend non
  vendables. La Phase 4 devra revérifier cette règle dans la transaction de
  création de commande ; aucun ajout à une commande n'existe encore ici.
- Permissions API distinctes : `menu.read`, `menu.write`, `menu.availability`.
  L'administrateur obtient les trois ; Réception obtient la lecture du menu.
  Les autres droits existants sont conservés. Les rôles personnalisés restent
  configurables par le propriétaire.
- Versions optimistes, verrou partagé avec les mutations d'accès et nouvelle
  vérification des droits dans la transaction : un acteur révoqué ou une fiche
  périmée ne peut pas écraser les changements en cours.
- Photos JPEG/PNG/WebP, 2 Mo et 16 mégapixels maximum ; sortie JPEG privée,
  métadonnées supprimées, lecture authentifiée sans cache. Comme pour le
  Personnel, les fichiers détachés restent privés ; aucune purge silencieuse.
- Routes `/api/v1/menu/categories`, `/items`, `/:id/prices`, `/:id/availability`
  et photos documentées par OpenAPI. `/api/v1/capabilities` confirme la présence
  du catalogue ; le web ne l'affiche que si cette capacité et `menu.read` existent.

## Schéma et installation

Modèles `MenuCategory`, `MenuItem`, `MenuPriceHistory` avec index, clés étrangères
restrictives et identifiants stables. Le suivi baseline reçoit deux migrations
additives : `202610090001_menu` (permissions) et `202610090002_menu_tables`
(tables). Ces étapes sont conservées séparées dans l'historique local appliqué.
La baseline Phase 2 et ses empreintes ne changent pas.

La génération de diff Prisma nécessite ici `--config database/prisma.config.ts` ;
vérifier le SQL produit, pas seulement le code de sortie. Le premier contrôle
d'intégration a détecté l'absence des tables après la seule étape permissions ;
la seconde migration a ajouté le schéma et l'ensemble a été revérifié.

Pour une base **neuve et vide** : `npm run db:bootstrap`, puis `npm run db:seed`.
Pour une base locale déjà sur la baseline contrôlée : `npm run db:deploy:baseline`.
**Ne pas exécuter ces commandes sur la base historique Hostinger.** Son SQL
Personnel manque encore ; les nouvelles migrations ne sont pas ajoutées à la
piste historique tant que celle-ci n'a pas été réconciliée et testée sur copie.

## Livraison et reste à faire

Le code source est destiné à `main` ; le web compilé compatible est publié dans
`hostinger-web`. Le web peut être livré avec l'API Phase 2 toujours en service :
le catalogue reste masqué tant que le serveur ne propose pas ses capacités.
Cette compatibilité ne vaut pas activation de Phase 3 sur le serveur.

Pour activer : sauvegarder et tester la restauration du serveur, réconcilier
l'historique Prisma sur une copie, appliquer les évolutions validées, livrer
l'API privée compatible, puis contrôler santé, catalogue et permissions en HTTPS.
Ne pas pointer Passenger vers une release Phase 3 avant la préparation du schéma.
Le déploiement GitHub générique Hostinger ne réalise aucune de ces opérations
privées. L'utilisateur confirme disposer de phpMyAdmin ; commencer par le relevé
de l'historique en lecture seule, puis une sauvegarde et une restauration isolée.

La Phase 3 est **développée et testée localement pour ce premier lot**, mais
reste ouverte jusqu'à activation serveur et recette utilisateur du catalogue.

### Étape phpMyAdmin suivante (lecture seule)

Sélectionner la base LYNE dans phpMyAdmin et exécuter
`database/diagnostics/hostinger-phase3-readonly.sql`. Relever les noms/empreintes
et états des migrations ainsi que les tables présentes. Ce diagnostic ne lit
aucune ligne métier et ne change rien. Ne pas exécuter la baseline ou le SQL de
reconstruction Personnel depuis phpMyAdmin. L'accès phpMyAdmin confirmé ne prouve
ni sauvegarde, ni restauration, ni réconciliation : ces étapes restent à exécuter.
